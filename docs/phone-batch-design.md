# 单观察多动作（`phone_batch`）设计

状态：最小版本已实现（2026-10-18），尚未在真机任务里统计效果。前提：动作回传（每个输入动作的回复里附带稳定后的画面）已经实现。

## 实现与草案的差异

- **返回值**：用 `completed`（已执行的步数）代替逐步的 `steps` 数组。停下时另给 `stoppedAt`（等于 `completed`）和 `stopReason`。`uncertain:true` 表示停下的那一步可能已经部分执行。
- **检查时机**：每一步的检查都放在它执行之前，尽量晚做。具体做法是先等上一步稳定，再一次读屏，同时得到两样东西：上一步的“区域外签名”（检查用）和本步的“区域外签名”（下一次比对的基准）。这样，上一步迟到的反应，比如延迟弹出的联想列表，也能拦在本步之前。
- **高影响词**：不只检查最后一步，每个点击和长按都检查；匹配范围是观察时的文字、描述和 view id。
  - 第一步命中时，整批按普通拒绝返回（`HIGH_IMPACT_SINGLE`），观察保留。
  - 后面的步骤命中时，前面的步骤照常执行，停在这一步。
- **新增的两条规则**：
  - 既无文字也无描述的点击目标，如果不是输入框或开关，就留给单步，因为无法判断它是不是“发送”之类的按钮。
  - `ENTER` 只允许出现在“向搜索框输入”之后，因为聊天框里的回车就是发送。
- **其他限制**：
  - 同一元素在一批里只能出现一次。
  - 所有步骤的文字合计不超过 8000 字，以免超出 64 KiB 的请求上限。
  - 整批限时 15 秒，到时以 `BATCH_TIME_LIMIT` 停下，保证在插件 25 秒的传输超时之前返回。
- **停止原因**：
  - `WINDOW_CHANGED`、`SCREEN_CHANGED_ELSEWHERE`、`BATCH_TIME_LIMIT` 只作为停止原因出现，不是错误码。
  - 目标变了沿用 `NODE_STALE`。
  - 上一步没有稳定下来时报 `SCREEN_SETTLING`。
  - 用户中途接管时报 `USER_CONTROL`，此时不读屏。
- **暂停策略**：第一步执行之后，任何停止都按成功结果返回，避免模型重做已经执行的步骤。遇到边界违规，照样暂停任务。

## 结论

- **值得做，但收益比动作回传小，且只适合一类场景**：所有目标都已出现在同一屏上，而且前面几步只会改变自己那一小块的操作，比如填表单的多个输入框、在设置页勾选多个开关，或者“输入搜索词后回车”。
- **核心原则是用错时自动退回单步，而不是放宽限制**：每一步之后，Broker 都核验画面是否只在刚操作的位置发生了变化。只要别处有变化（新页面、弹窗、联想列表、列表重排），就立刻停下，剩余步骤不执行，并返回当前画面。这样即使模型用错，代价也接近“只执行了第一步的单步调用”，不会点错地方。
- **建议排在动作回传真机验证之后**：先用真实任务确认动作回传省下的步数，再按任务类型决定是否值得做。

## 数据（2026-10-17 知乎 session，紧凑格式部分）

| 指标 | 数值 |
|---|---|
| 模型步数 | 553 |
| 平均每步的上下文 | 约 13 万 token（97.9% 命中缓存），每步耗时中位 2.5 秒 |
| 前后相邻、同一轮内、都成功的动作对 | 87 |
| 其中第二个动作的目标早已原样出现在第一个动作所用观察里（文字和位置都相同） | 11（约 13%） |

其余约 87% 的动作对，第二个目标是第一个动作之后才出现的：点进文章、打开搜索页、弹出联想列表、出现弹窗。这种情况一次观察根本规划不出第二步，批量没有用武之地。

按这条 session 估算，批量最多省约 11 步（2%）。浏览信息流类任务收益很小；表单、筛选、设置、登录前的资料填写等任务会高得多。

**一个例子**：一屏上有 3 个输入框和 1 个“下一步”按钮。
- 逐步执行要 4 步，约 52 万 token 的上下文，耗时约 15 秒。
- 批量执行只要 1 步，约 13 万 token，耗时约 5–6 秒（每步之间等画面稳定约 0.5–0.9 秒）。

## 何时能用，何时不要用

**能用**（全部满足）：
1. 所有步骤的目标都是**同一次观察**里的元素（`elementId`），不用坐标。
2. 除最后一步外，每一步都只改变它自己：往输入框写字（`type_text`），切换勾选框、开关或单选项，在多选模式里勾选列表项。
3. 最后一步可以导航：点“下一步”、“搜索”，或按 `ENTER`、`BACK`。
4. 这一屏的界面树完整（`complete` 不是 `false`），上一个动作的回复里没有 `settled:false`。

**不要用**：

| 情形 | 原因 |
|---|---|
| 后面的目标要等前一步之后才出现（联想词、下拉菜单、弹窗、二级菜单、“加载更多”） | 观察里还没有这个目标，或者有一个碰巧同 ID 的错误目标 |
| 中间某一步会跳转（打开文章、切换标签页、点链接、打开菜单） | 跳转之后剩下的目标全部失效；跳转只能放在最后一步 |
| 滑动、滚动 | 内容整体位移，只能作为最后一步，或者干脆单独调用 |
| 信息流、轮播、视频、倒计时、自动刷新的列表 | 节点一直在动，核验会频繁中止 |
| 界面树不完整、自绘界面、WebView、目标来自截图坐标 | 元素 ID 不可靠，无法核验 |
| **发送、付款、删除、授权、下单、发布等高影响操作** | 必须单独调用，并且先看过画面；批量里出现这类操作时，Broker 会在执行这一步之前停下 |
| 刚出现 `observationError`、意外的 `changed:false`，或刚交还接管 | 对画面的认识不可靠，应该先单步确认 |

## 工具形状

```json
phone_batch {
  "observationId": "<一次 phone_ui_tree 或动作回传的观察>",
  "steps": [
    { "tool": "type_text", "elementId": "n12", "text": "张三" },
    { "tool": "type_text", "elementId": "n15", "text": "13800000000" },
    { "tool": "tap",       "elementId": "n20" },
    { "tool": "key",       "key": "ENTER" }
  ]
}
```

- `steps` 为 2–5 步。`tool` 只能取 `tap`、`long_press`、`type_text`、`key`。
- `tap`、`long_press`、`type_text` 必须带 `elementId`；`key` 只能取 `ENTER` 或 `BACK`，而且只能是最后一步。
- 没有坐标、`swipe`、`scroll`、`wait`、`launch_app`、`HOME`。需要这些操作，就说明这一步不该放进批量。
- 插件在发出请求前先做两项静态检查（不满足就不发请求）：
  - 每个 `elementId` 都在这次观察里；
  - `type_text` 的目标带 `e` 标志。
- 这次观察在批量开始时就被消耗掉（一次性），和单步坐标动作一样。

## Broker 每一步的守卫

每执行一步之前和之后都要核验，任一不满足就**停止**，剩余步骤不执行：

1. **执行前核验目标**：节点仍然存在、可见、可用，位置偏差不超过 3 像素。这一点沿用 `ProfileStructure.live`，但要**新增文字和描述比对**。RecyclerView 会复用视图，同一个节点句柄、同一个位置，可能已经显示别的内容，只比位置拦不住这种情况。
2. **窗口结构不变**（非最后一步）：执行后，结构指纹（窗口集合、前台 UID）必须和执行前相同。新 Activity、弹窗、下拉框、联想浮层都会改变它，于是停止。
3. **只允许局部变化**（非最后一步）：执行后等画面稳定，然后对所有带文字的节点算签名，但排除与刚操作节点区域相交的节点；这个签名必须和执行前一致。
   - 输入框里文字变化、出现“清除”图标、勾选状态变化，都不算违规。
   - 别处出现提示文字、计数器变化、列表重排，都会停止。这是有意偏保守的设计。
4. **高影响词停止**：最后一步如果点击的节点文字或描述命中“发送、付款、支付、删除、确认、授权、购买、下单、发布”（含英文对应词），就不执行这一步，停止原因记为 `HIGH_IMPACT_SINGLE`，让模型单独调用。这只是兜底，主要约束仍在提示词里。
5. **取消、暂停、接管**：每一步之间都检查一次，命中就停止。
6. **注入不确定**（按下之后出现异常）：立即停止，结果里标为不确定，不重试。

## 返回格式

```json
{
  "performed": true,
  "steps": [ {"index":0,"performed":true}, {"index":1,"performed":true}, {"index":2,"performed":false} ],
  "stoppedAt": 2,
  "stopReason": "SCREEN_CHANGED_ELSEWHERE",
  "changed": true,
  "observation": { "...": "与 phone_ui_tree 完全相同，新的 observationId" }
}
```

- 停止原因包括：
  - `TARGET_CHANGED`（目标不在、移动或文字变了）
  - `WINDOW_CHANGED`
  - `SCREEN_CHANGED_ELSEWHERE`
  - `HIGH_IMPACT_SINGLE`
  - `CONTROL_INTERRUPTED`
  - 以及单步动作本来就会给出的拒绝码，如 `NODE_STALE`、`NOT_EDITABLE`、`SECRET_INPUT`、`INPUT_REJECTED`
- 无论完成还是中途停止，都附带稳定后的画面，模型从它继续。
- 第一步执行之前就被拒（比如目标已失效）时，整体按普通拒绝返回，观察保留，与单步的 `KEEPS_OBSERVATION` 规则一致。

## 用错的代价

| 误用方式 | 拦截它的守卫 | 结果 |
|---|---|---|
| 第二步的目标要等第一步之后才出现，但模型用了当前屏上一个碰巧存在的 ID | 第一步之后窗口或内容在别处变化 | 只执行了第一步，返回新画面 |
| 中间一步其实会跳转 | 窗口结构变化 | 同上 |
| 列表复用视图，同一位置换了内容 | 执行前的文字比对 | 在这一步之前停止 |
| 第一步触发弹窗或联想浮层 | 窗口结构变化 | 停止，模型看到弹窗 |
| 把“发送”放进批量 | 高影响词停止，加上提示词规则 | “发送”这一步不执行 |
| 守卫过于保守，误停 | 无 | 只是没省到步数，效果等同逐步执行 |

剩下的风险是守卫拦不住的情况：同一窗口内、操作区域以外没有任何带文字的节点变化，但语义已经变了，例如无文字的自绘按钮换了功能。所以批量**只接受元素 ID**、**界面树必须完整**，这两条限制要保留。

## 与并行工具调用的关系

DSH 允许模型在一步里同时发出多个工具调用（session 第一步就同时调了 `phone_status` 和 `phone_apps`）。动作回传之前，同一观察上的两个元素操作会被串行执行，第二个不受任何检查，等于一个没有守卫的批量。动作回传之后，第一个动作会把观察换成新的，第二个调用会因观察过期被拒（`STALE_OBSERVATION`）。

`phone_batch` 是唯一带守卫的多动作方式。提示词里应写明：不要用并行调用代替它。

## 分阶段落地

1. **先测动作回传**：用真机任务统计“动作后再调 `phone_ui_tree`”还剩多少，以及 `changed:false` 之后模型是否还会重复操作。
2. **最小版本**：只支持“若干 `type_text`/勾选 + 一个最后动作”，最多 5 步，实现上述全部守卫，并加 JVM 测试（局部变化签名、文字比对、高影响词表）。
3. **验收指标**：
   - 表单类任务的模型步数下降；
   - 批量中途停止率，以及各停止原因的分布；
   - 守卫没拦住、真的点错的次数，目标为 0，需要人工抽查截图。
4. 如果中途停止率长期很高，说明模型在不适合的场景里使用批量。这时收紧提示词，或者把工具只暴露给特定任务。

## 未决问题

- 局部变化规则里“与刚操作节点区域相交”的判定，要不要放宽一点（比如输入框下方紧贴的校验提示）？先保守，看停止原因的分布再定。
- 高影响词表放在哪里维护：中英文词表写进 Broker，还是由插件下发？倾向写进 Broker，与其他安全规则放在一起。
- 批量期间任务岛的动态如何展示（逐步显示，还是合并成一条）。
